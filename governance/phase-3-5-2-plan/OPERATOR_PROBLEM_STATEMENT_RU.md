# Operator Problem Statement (RU)

**Дата:** 2026-05-26  
**Контекст:** Phase 3.5.1 hands-on demo, Review Assistant Thin v0.3

---

## Проблема

Система **уже работает**, но оператору **трудно её почувствовать**, потому что:

| Боль | Пример |
|------|--------|
| Нужно помнить команды | `python prototypes-derived/review-assistant-thin/minimal_demo.py --scenario missing_approval` |
| Нужно знать имена сценариев | `critic_uncertain` vs `bad_draft` — неочевидно |
| Нужно понимать TRACE | `- approval_timeout` — что это значит для безопасности? |
| Нет русского пояснения результата | `decision=BLOCKED` — ок, но **почему**? |
| Нет меню | Нельзя выбрать «2» вместо длинной команды |
| Нет сохранённого отчёта | Закрыл терминал — показать команде нечего |
| Нет ощущения «я управляю агентом» | Скорее «я запустил тестовый скрипт» |

Дмитрий **вручную** прогнал 9 сценариев и **понял**, что агентный контур живой. Но путь к этому пониманию — через governance docs + длинные команды + сырой trace.

---

## Почему это важно

Если **оператор** не может быстро понять demo:

- **стажёры** потеряются на первом же `--scenario`;
- **stakeholders** не увидят ценность без сопровождения;
- **следующий агент** (Task Triage) снова останется «только документы»;
- проект будет восприниматься как **репозиторий markdown**, а не lab с живым поведением.

Phase 3.5.1 зафиксировала: **технически всё ок**. Phase 3.5.2 должна спланировать: **как сделать это человекочитаемым**.

---

## Что должно улучшиться

Demo Runner (будущий) должен:

1. **Не менять** `minimal_demo.py` и решения агента.
2. **Оборачивать** существующие команды.
3. **Объяснять** результат по-русски.
4. **Показывать** меню с понятными названиями.
5. **Предупреждать** перед real provider.
6. **Опционально** сохранять transcript для демо другим людям.

---

## Что Demo Runner **не** решает

- Не заменяет production UI.
- Не даёт free-form ввод задачи (это Phase 3.5.3+).
- Не делает interactive approval в runtime.
- Не доказывает качество модели.
